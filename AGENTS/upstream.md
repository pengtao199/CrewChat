# 上游同步（vendored 基座）

## 适用范围

改动 `codeg/`、`ccr/` 里的上游代码，或需要跟进它们的新版本时。

## 目标

在复用成熟上游的同时保持可回退、可对比、可升级，不让二次开发变成无法维护的黑盒。

## Vendored 基座

| 目录 | 上游 | 许可 | 角色 |
| --- | --- | --- | --- |
| `codeg/` | `spacering-net/codeg` | Apache-2.0 | 协作工作台（Next.js 前端 + Tauri/Server 后端） |
| `ccr/` | `musistudio/claude-code-router` | MIT | 统一模型管理（本地网关 + 控制面） |

各自的取舍、改动清单、构建与升级方式在**同目录的 `NOTICE.md`**，那里是唯一权威。

## 原则

- **改动最小化**：能用上游已有配置/插件解决的不改源码；能新增文件解决的不改上游文件。
- **自有代码可自由演进**：我们新增的文件/目录（如 `codeg/src/components/settings/ccr/`、`src/lib/ccr*.ts`）可随意拆分重组，不影响上游升级。
- **结构拆分（🟠）是允许的例行操作**（2026-10-12 起，用户拍板）：上游大文件拆为模块目录、内嵌测试外移（`foo.rs` → `foo/mod.rs` + `foo/tests.rs`）、大段代码按域移入子文件，前提是**行为不变、公共 API 不变、全量测试绿**，并把「上游文件 → 本仓库结构」登记到 `NOTICE.md` 的拆分表。拆分只为可维护性与可审阅性；禁止借拆分之机重写逻辑。
- **改动分四档**：🟢 新增文件自由改；🟠 结构拆分（见上）；🟡 上游文件小补丁（`[crewchat]` 标记 + `NOTICE.md` 登记、保持 diff 最小，如设置壳导航与 i18n 文案）；🔴 结构性重写尽量避免——宁可绕路（加新页面 / 新入口），不重写旧组件。协议核心（`acp/`、`parsers/`、`delegation/`、路由骨架）的**逻辑**只做注册型小补丁，但同样允许上面的结构拆分。
- **升级按需、用三方重放**：不追每版；需要新特性（如委派 v2）或累积修复时升级一次。升级时以旧 vendored 版本为基线，对新上游做 diff，把 `[crewchat]` 改动当补丁逐个应用；**拆分过的文件按 `NOTICE.md` 的拆分表重放**（上游对 `foo.rs` 的改动 → 应用到场内对应块）；机械改动（i18n）用脚本重放，方法记入 `NOTICE.md`。
- **上游文件可辨识**：所有对上游文件的改动加 `[crewchat]` 前缀注释，`rg '\[crewchat\]' <dir>` 可列出。
- **命名空间隔离**：不占用上游既有路径与命名；新增能力放我们的命名空间。
- **署名保留**：各基座的 `LICENSE` 原样保留，不删除版权头与 `@license` 注释。

## 具体规则

- 升级时按对应 `NOTICE.md` 的步骤重放改动，而不是整体覆盖目录。
- 升级前先记录新的 upstream commit；升级后更新 `NOTICE.md` 的 Vendored commit。
- 只读的上游参考放 `Reference/`（不入库）；不把 `Reference/` 当成本仓库代码。
- 上游自带的 `AGENTS.md` / `CLAUDE.md` 是各自子系统的开发指引，不是本仓库的规则文件；
  本仓库规则始终以根 `AGENTS.md` 为准。
- 不整体替换 vendored 目录来“同步最新”；那会丢掉我们的改动。

## 检查

- 这个改动是新增文件还是改了上游文件？改上游的必要性写下来了吗？
- 改动处有 `[crewchat]` 注释吗？对应 `NOTICE.md` 更新了吗？
- 如果这是结构拆分：行为与公共 API 变了吗（应当不变）？全量测试绿了吗？拆分表登记了吗？
- 如果上游下周改了同一处，我知道怎么重放吗（拆分过的文件查 `NOTICE.md` 的拆分表）？
